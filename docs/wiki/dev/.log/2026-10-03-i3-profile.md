**Durable knowledge:**
- **A profile is a set of ids, nothing else.** It executes no check of its own; the registry's resolution
  is the only truth, so a profile cannot disagree with the report.
- **`NotApplicable` passes a profile; an external prerequisite in a profile is a profile bug.** The first
  is what lets one profile serve a gateway node and a plain provider; the second is why the three
  `not_verifiable_here` ids are in no profile — they would refuse every node.
- **Adding a requirement is a release note.** The set is pinned by a test that the checklist copies; a
  revision bump is the signal.
- **The profile's own acceptance test found the next gap:** `id.ca_key_off_node` can never be enforced on
  a running node — `tls::load_or_create_ca` needs the CA key and mints a new CA without it. It is in the
  registry (reported truthfully) and out of `secure-single-domain` rev 1, with the reason beside the set.
