# ingest — 360° review of v2.4.0..HEAD: three pooling bugs + FsStore erase serialization (2026-09-02)

A full review of everything shipped since the `v2.4.0` tag (erase verb, py connection pool, h2
bump, nightly scheduler). CI green throughout; these are the things CI couldn't see. All fixed
same day.

**Bugs found and fixed:**

1. **`TupleSpace.take`/`take_by_key` missed by the 0.2.0 pooling conversion** — still a fresh
   `AsyncClient` per call. This is the *worker hot loop*: with items available, `take` returns
   immediately, so a busy worker was one TCP connection per claimed item — the exact
   ephemeral-port regression 0.2.0 shipped to kill, on the API most likely to run at ~16k-call
   rates. Now pooled with the per-borrow timeout (`asy(timeout=timeout_secs + 5.0)`).
2. **`MyceliumAgent.set_with_min_acks` missed too** (fresh sync client per quorum write) — now
   `sync(timeout=timeout_secs + 2.0)`.
3. **`ClientPool.asy()` evicted live sibling loops** — eviction popped every entry whose key
   wasn't the current loop, with no liveness check, and the map was mutated without the lock.
   Two threads each running a live loop (a normal worker topology) would evict each other's
   client on every miss. Now: entries store `(loop, client)` (pinning the loop object also
   prevents `id()` reuse), eviction only for `loop.is_closed()`, all map access under the lock
   (never held across I/O).
4. **`FsStore` had no erase-vs-write serialization** — `GitStore` serializes through
   `write_lock` + ref CAS; `FsStore` relied on per-object CAS, which resolves write-write races
   but not `remove_page` (a multi-object delete) interleaving with a write recreating the page
   mid-erasure → a persistent torn page (manifest surviving with sections deleted). Fix: flat
   leaf `FsStore::mutate` mutex over all four mutators — [lock-order](../concurrency/lock-order.md)
   row 35. In-process only, honestly documented: cross-process the CAS + idempotent-erase retry
   remains the (weaker) backstop.

**Testing lessons (the part worth keeping):**

- **Timing-based concurrency tests can silently prove nothing.** The first attempt at a
  regression test for bug 3 (two threads + a start barrier) *passed on the pre-fix code*: the
  barrier synchronized both first borrows so each saw an empty map before either inserted —
  eviction never ran. Even a staggered start self-damped (3 clients, not the theoretical ~100)
  because the burst finished inside the other thread's scheduling gap. The reliable gate is
  **deterministic**: drive two `asyncio.new_event_loop()`s directly and assert the eviction rule
  itself (live sibling kept, closed loop evicted) — `test_pool_evicts_only_closed_loops_never_
  live_siblings`, which does fail pre-fix. Verify every new concurrency test against the broken
  code before trusting it.
- The FsStore tripwire asserts wholeness **after** each race round, not during: a reader
  entering via the manifest before an erase may transiently error *by design* (manifest deleted
  first); the bug is the persistent torn state.
- **The connection-reuse gate wasn't in CI** — `ci.yml`'s pytest line only ran
  `test_typed`/`test_reason`. Added; it needs no node (stub server).

**Residual (recorded, deliberate):** `prompt_skill.py`/`reason.py` still hold an eager
`AsyncClient` from `__init__` (the loop-binding hazard `_pool.py` documents) and `a2a.py` a
third lifecycle pattern; the triplicated CAS retry skeleton in `git_store.rs`
(write_with/write_pages/remove_page) and the triplicated `15.0` pool timeout in the py SDK are
reuse debt, not bugs. mycelium-py 0.2.0 → **0.2.1**.
