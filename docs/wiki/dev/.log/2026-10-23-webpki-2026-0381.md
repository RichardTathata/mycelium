## [2026-10-23] ingest | rustls-webpki 0.103.16, webpki-roots and webpki-root-certs 1.0.10 (RUSTSEC-2026-0381..0383)

- Three advisories published 2026-10-19/20 turned `Dependency audit (RUSTSEC)` red, first seen on #655's last run.
  -0382: `rustls-webpki` may accept a distrusted intermediate when the configured anchors allow such a path. -0381 and
  -0383: the bundled root stores (`webpki-roots`, `webpki-root-certs`) allowed trust in distrusted emSign
  intermediates.
- Patch bumps in all three tracked lockfiles (#661). cargo also normalised stale edges within their declared ranges:
  four `windows-sys` edges 0.52.0 → 0.61.2 in `examples/conway-gpu/Cargo.lock` (`cfg(windows)`, both versions already
  locked) and `tempfile`'s `getrandom` edge 0.3.4 → 0.4.3 in `fuzz/Cargo.lock` (already locked at the root; the fuzz
  job runs on push, not on PRs, so that edge was unexercised by the PR's CI).
- Exposure, read from the code by the independent review of #661: `rustls-webpki` verifies the mesh's mTLS both ways
  (`mycelium-core/src/tls.rs` `WebPkiClientVerifier`/`WebPkiServerVerifier`) against the operator's CA alone, so
  -0382's path cannot arise there; gateway TLS is server-only (`with_no_client_auth`); the federation client pins an
  SPKI. The node's `reqwest` 0.12 clients are native-tls (`Cargo.toml` declares `reqwest` with default features, and no
  call site selects rustls), the object-store client uses `rustls-platform-verifier` (on Linux: `rustls-webpki` over the OS store — the one
  shipped path where -0382 applies against public anchors; on macOS the Security framework), and `webpki-root-certs` is a
  wasm32-only dependency — **no shipped build consults a bundled root store**, so -0381/-0383 are defence in depth.
  `rustls-webpki` by tag (v2.0.0:0.103.13 v2.3.0:0.103.13 v2.8.0:0.103.15 v2.20.0:0.103.15 v2.30.0:0.103.15 v2.36.1:0.103.15): present since the first tagged release.

Lesson: the first draft of the changelog entry said the bundled stores were "consulted by the outbound clients",
which was the *shape* of a reqwest+rustls build, not this one's — an exposure statement is read from the resolved
feature graph (`cargo tree -e features`), not from which crates the lockfile contains.
