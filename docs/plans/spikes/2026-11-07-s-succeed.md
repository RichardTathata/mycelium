# Spike S-succeed — a `cert_pem` node takes a successor CA's certificate without a restart

**Date:** 2026-11-07. **Plan:** [`identity-and-lifecycle.md`](../identity-and-lifecycle.md), wave 1b. This spike settles
row I2 (D4). **Code:** branch `spike-s-succeed`, commit `abf6b135`, off `main` at `6a64e8bc`. The code is throwaway and
is not for merge (D8: no spike ships).

**The question, from the plan:** can a node on `cert_pem` (secure profile, no CA key) take a certificate issued under a
successor CA **without a restart**? The plan names a reload path through `activate`, a two-root `RootCertStore`, and
`verify_member_cert` across the window.

**Answer:** **yes**, given a reload path that `main` does not have today. The cutover adds about 1.3 ms. The re-root does
**not** survive a restart, so I2 must persist the trust it installs. No restart is needed inside the window.

## What `main` has, and why a restart is required there today

- **`NodeTls::activate`** (`mycelium-core/src/tls.rs`) swaps the signing key, the mesh server and client configs, the
  gateway key and the node certificate. Each is behind an `ArcSwap`, and a connection reads them when it starts: the
  accept side's `tls_accept` (`src/agent/tasks.rs`) and the dial side (`mycelium-core/src/writer.rs`).
- **Two pieces are fixed for the node's life.** `cert_verifier`, the chain check behind `verify_member_cert`, and
  `fleet_server_verifier`, the bulk fetch's server check, are not swapped. Their doc comments say so: "rotation reuses
  the CA".
- **No material path exists without the CA key.** The only way to make `RotationMaterial` is `generate_rotation_after`,
  and it calls `load_existing_ca`, which needs `ca-key.pem`. The secure posture does not hold that file.
- **One root, read once.** `build_rustls_configs` builds a root store of exactly one CA certificate. `pem_cert_to_der`
  takes only the **first** certificate in `ca_cert_pem`, so a two-certificate PEM file does not give two roots at
  start either.

## What the spike added (about 90 lines, `mycelium-core/src/tls.rs`, `src/agent/mod.rs`)

- **Swappable chain checks.** `cert_verifier` and `fleet_server_verifier` are now `ArcSwap`, and `activate` swaps them
  when the material carries new ones. A same-CA rotation carries `None`, so its behaviour is unchanged.
- **`build_rustls_configs_roots`:** the mesh configs over a root store of several CA certificates.
- **`reroot_material(cert_pem, key_pem, roots, …)`:** `RotationMaterial` from a pre-issued certificate and key plus the
  given roots. It needs no CA key.
- **`issue_node_cert_for_key`:** the issuer's host re-issues a node's **existing** key under a CA. This is the
  successor issuing for the current key, not a new key.
- **`GossipAgent::spike_reroot`:** publishes the certificate record (as `rotate_identity` does), then calls `activate`.

## What ran

The test is `agent::spike_s_succeed_tests::spike_s_succeed_a_cert_pem_node_re_roots_live`, run with `--features tls`.
Each node is a live `GossipAgent` on `cert_pem` and `key_pem` issued by `mycelium tls issue`'s function. Each has
`ca_cert_pem` pointing at the CA certificate and no `ca-key.pem` in its directory; the test asserts that before and after
start.

The handshakes in steps 1, 2 and 4 drive each node's **live** configs (`client_config()` / `server_config()`) in memory.
A session is proved by a KV write crossing the mesh. Neither `peers()` (what membership believes) nor
`connected_peers()` (writer entries, which exist while a writer retries a failing connect) shows that a handshake
succeeded. An early version of this test was fooled by both.

| Step | State | Observed |
|---|---|---|
| 0 | A and B on CA1 certificates, CA1 trust. Control: a fresh CA1 node E joins | E's first write reached A in **9.98 s** (twice) |
| 1 | B takes its key re-issued under CA2, live, trusting CA1 and CA2. A still trusts CA1 only | New handshakes between A and B refused both ways (`BadSignature`, below). B's write after the cutover reached A in **27 ms** over the existing session. The cutover (material and `activate`) took **1.2–1.4 ms** |
| 2 | A widens to both roots live, keeping its CA1 certificate | B (CA2) to A, and A to B: both handshakes succeed. A's `verify_member_cert` accepts B's CA2 certificate, which it refused before step 1 |
| 3 | A fresh node C on a CA2 certificate dials live A | C's first write reached A in **9.95 s**, the same as the control: a real mesh mTLS session under the new root on a node that never restarted |
| 4 | A takes its own CA2 certificate and narrows to the CA2 root only. A fresh CA1-only node D dials A | B (CA2) to A succeeds. D refused both ways, and D's write never reached A within 3 s. Membership still lists D, as a belief and not a session |

**Repeats:** seven runs passed of seven (five, then two with the control). The ~10 s for a new node's first write is
the ordinary join path: the control measured it with no re-root involved. The spike does not explain it.

## What it found that I2 must say

1. **Order is the protocol.** Every node widens its trust to both roots **before** any node presents a successor
   certificate. A node that cuts over early can no longer handshake with peers that trust only the old root, in either
   direction. Its existing sessions carry on, so the failure shows only at the next reconnect.
2. **A restart reverts the re-root.** The node comes back on whatever `cert_pem` and `ca_cert_pem` name, and
   `ca_cert_pem` yields one root. Without persistence, a node restarted mid-window comes back trusting only one CA. So
   I2's act-once-persist (D4) has to cover two things: the trust set, as several roots, or the plan's `ca-commit.pem`
   read alongside; and the node's current certificate file.
3. **Every minted CA has the same subject.** `generate_ca` uses rcgen's default distinguished name, so CA1 and CA2 share
   a subject name. The webpki refusal therefore reads `BadSignature`, not `UnknownIssuer`. Two same-named roots in one
   store still worked (step 2): the path builder tried both. I2 should still give a successor a distinct subject so a
   refusal says what it is. The spike did not test how other verifiers handle same-named roots.
4. **Which key after succession.** The spike re-issued each node's **current** key under the successor CA, so no key
   history or identity record changed and the existing revocation standing held. `rotate_identity` still cannot run on
   an off-node posture (it needs the CA key). A new key under the successor CA was not tried: it would need rotation's
   identity records too.

## What it could not do, or did not try

- **The successor-signed record and `tls commit` / `tls succeed`.** D4's record, its window end, and acting once were
  not built. The spike only calls the reload path by hand.
- **Persistence across a restart.** Shown to be needed (finding 2), not built.
- **The gateway on its own `[gateway_tls]` certificate.** Untested; the node-certificate gateway reads `gateway_key`,
  which `activate` swaps.
- **The bulk fetch.** It reads `fleet_server_verifier()` per fetch (`src/agent/bulk.rs`), so it should follow the swap;
  not exercised.
- **Certificate records after narrowing.** Once a node narrows to the CA2 root, its `verify_member_cert` stops accepting
  CA1-issued certificate records. That can change what `own_history` and the revocation fold count for keys anchored
  only by CA1 records. Not measured. I2 has to decide whether old records keep standing after the window.
- **Removal and revocation across the two roots, a mixed-version fleet, and the secure profile's guarantee report**
  during the window.
- **Certificates issued under a CA2 intermediate rather than a second root.** Not tried.
