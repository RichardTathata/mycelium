# Spike S-succeed: a `cert_pem` node takes a successor CA's certificate without a restart

**Date:** 2026-11-07. **Plan:** [`identity-and-lifecycle.md`](../identity-and-lifecycle.md), wave 1b. This spike settles
row I2 (D4). The note was revised after #732's adversarial review.

**Evidence:** tag **`spike/s-succeed-2026-11-07-r2`** (commit `f793cd5f`, on branch `spike-s-succeed`, off `main` at
`6a64e8bc`). It holds the code the final batch ran (`71f234cb`) and that batch's raw logs, under
`spike-evidence/s-succeed-2026-11-07/`. The tag keeps the evidence after the branch is deleted. The earlier tag
`spike/s-succeed-2026-11-07` (`7b1ef71a`) is left in place, because tags are not moved. Its batch, and every earlier one,
is superseded and not quoted. The code is throwaway and is not for merge (D8: no spike ships).

**The question, from the plan:** can a node on `cert_pem` (secure profile, no CA key) take a certificate issued under a
successor CA **without a restart**? The plan names a reload path through `activate`, a two-root `RootCertStore`, and
`verify_member_cert` across the window.

**Answer:** **yes**, given a reload path that `main` does not have today. The re-root does **not** survive a restart, so
I2 must persist the trust set and the successor certificate. No restart is needed inside the window.

## What `main` has, and why a restart is required there today

- **What `activate` swaps.** `NodeTls::activate` (`mycelium-core/src/tls.rs`) swaps the signing key, the mesh server and
  client configs, the gateway key and the node certificate. Each sits behind an `ArcSwap`, and a connection reads its
  config when it starts: on the accept side in `tls_accept` (`src/agent/tasks.rs`), on the dial side in
  `mycelium-core/src/writer.rs`.
- **What it does not.** `cert_verifier`, the chain check behind `verify_member_cert`, and `fleet_server_verifier`, the
  bulk fetch's server check, are fixed for the node's life. Their doc comments say "rotation reuses the CA".
- **No path without the CA key.** `RotationMaterial` comes only from `generate_rotation_after`, which calls
  `load_existing_ca` and so needs `ca-key.pem`. The secure posture does not hold that file. #732's review also found
  that it saves the new key before the CA check fails, which leaves a stray key file; that is a separate follow-up on
  `main`.
- **One root, read once.** `build_rustls_configs` builds a root store of exactly one CA certificate, and
  `pem_cert_to_der` takes only the **first** certificate in `ca_cert_pem`.
- **Cached judgments.** These are found by the review and read from the code; the spike did not exercise them. The
  revocation fold's `cert_facts` caches each certificate's verdict by its hash and clears the cache only at 4,096
  entries. `merge_anchors_seen` keeps anchors for good. The KV arm's `certificate_record_proves_itself`
  (`connection.rs`) judges afresh each time. A change of roots on a live node therefore leaves the fold judging by the
  roots it had when it first saw a certificate. Row I2 covers this.

## What the spike added (`mycelium-core/src/tls.rs`, `src/agent/mod.rs`; test `src/agent/spike_s_succeed_tests.rs`)

- **Swappable chain checks.** `cert_verifier` and `fleet_server_verifier` are now `ArcSwap`. `activate` swaps them when
  the material carries new ones; a same-CA rotation carries `None`.
- **`build_rustls_configs_roots`:** the mesh configs over a root store of several CA certificates.
- **`reroot_material(cert_pem, key_pem, roots, …)`:** `RotationMaterial` from a pre-issued certificate and key plus the
  given roots, with no CA key.
- **`issue_node_cert_for_key`:** the issuer's host re-issues a node's **existing** key under a CA.
- **`GossipAgent::spike_reroot`:** writes the certificate record (as `rotate_identity` does), then calls `activate`. It
  does not clear `cert_facts` or touch `anchors_seen`.
- **Two knobs, for M1 only:** `SPIKE_HS_MS` sets `handshake_timeout_ms` and `SPIKE_HC_S` sets
  `health_check_interval_secs`, on every node.

## What ran

There is one test, `agent::spike_s_succeed_tests::spike_s_succeed_a_cert_pem_node_re_roots_live`, with **seven nodes**,
each a live `GossipAgent`:

| Node | Its certificate | Its trust | Role |
|---|---|---|---|
| A, B | CA1 at start | CA1 | the long-running pair |
| E | CA1 | CA1 | the control join |
| C | CA2 | **CA1 only**: it must verify A's CA1 certificate in step 3 | joins under the successor |
| G | CA2 | CA2 only | sees A's own successor certificate |
| F | CA1 | CA1, widened live to both roots | M2's peer |
| D | CA1 | CA1 only | cut off after narrowing |

Every node runs on `cert_pem` and `key_pem` issued by the function behind `mycelium tls issue`, with `ca_cert_pem`
naming its trust. No node has a `ca-key.pem` in its directory; the test asserts that before and after start.

**How sessions are judged.** The handshakes in the table below drive each node's **live** configs (`client_config()`
and `server_config()`) in memory. A socket session is proved by a KV write crossing the mesh. Neither `peers()`, what
membership believes, nor `connected_peers()`, the writer entries (which exist while a writer retries a failing connect),
shows that a handshake succeeded; an early version of the test was fooled by both.

| Step | State | Observed (final batch, all seven runs) |
|---|---|---|
| 0 | A and B on CA1. Control: E joins A | E's first write reached A in 9.97–9.99 s (default tick), or 1.97–1.99 s at a 2 s tick |
| 1 | B takes its current key re-issued under CA2, live, trusting both roots. A still trusts CA1 only | New handshakes between A and B are refused both ways with `BadSignature` (finding 3). B's write after the cutover reached A in 25.5–28.4 ms over the existing session |
| 2 | A widens to both roots live, keeping its CA1 certificate | B to A and A to B both succeed. A's `verify_member_cert` accepts B's CA2 certificate, which it refused before step 1 |
| 3 | C (CA2 certificate, CA1 trust) dials live A | C's first write reached A in 9.94–9.97 s (default tick), or 1.94–1.97 s at a 2 s tick: the same as the control. This is a real mesh mTLS session under the new root, on a node that never restarted |
| 4 | A takes its own CA2 certificate and narrows to the CA2 root only | B (CA2) to A succeeds. **L5:** A's write reached G in 26.1–28.8 ms, so A presented its own successor certificate on a socket. **M2:** F to A is `server refused … BadSignature`, A's narrowed **accept** side refusing an old-root certificate from a peer that trusts both roots; A to F is `client refused … BadSignature`, A's narrowed dial side. **Cutover cost (L2).** Each figure is timed inside the **same** `spike_reroot` call, B's in step 1:
- building the material: 0.97–1.14 ms;
- the certificate-record write: 217–242 µs;
- `activate`: 23–26 µs;
- the whole call: 1.23–1.40 ms.

**M1: what bounds a join, a finding about `main`.**
- **Measured, the attribution to the knobs.** Each knob was set on **every** node.
  - At `handshake_timeout_ms = 2000` the joins were unchanged. Control / C: 9.99 / 9.95 s (`hs2000-1`) and
    9.97 / 9.97 s (`hs2000-2`).
  - At `health_check_interval_secs = 2` both fell to about 2 s. Control / C: 1.99 / 1.94 s (`hc2-1`) and
    1.97 / 1.97 s (`hc2-2`).
  - The opposite direction, a running node's write reaching a newly joined one (G, step 4), took 26–29 ms.

  So join time tracks `health_check_interval_secs` and not `handshake_timeout_ms`.
- **Inferred, not measured, the mechanism.** A write a node makes as it starts, before its first connection is up,
  is carried by anti-entropy rather than a direct push. That is the health monitor's `request_state` on each tick
  (`src/agent/tasks.rs:600–605`, `650–656`, `828–846`), answered in `mycelium-core/src/connection.rs:704–835`, which
  ignores a `StateRequest` from a peer the receiver does not yet know.
- **Not attributed: whose tick it is,** the joining node's or A's. The knob was set on all nodes at once, so the
  batch cannot tell them apart.

The spike changes none of this. It is filed separately (PR body).

## What it found that I2 must say

1. **Order is the protocol.** Every node widens its trust to both roots **before** any node presents a successor
   certificate. A node that cuts over early can no longer handshake with peers that trust only the old root, in either
   direction, while its existing sessions carry on (step 1). So the failure shows only at the next reconnect.
2. **A restart reverts the re-root.** The node comes back on whatever `cert_pem` and `ca_cert_pem` name, and
   `ca_cert_pem` yields one root. Without persistence, a node restarted mid-window comes back trusting only one CA. That
   follows from the code as read; no restart was run.
3. **The issuer is matched by name.** Every minted CA carries rcgen's default subject, and `generate_node_cert` rebuilds
   the signing CA from the same fixed parameters, so every node certificate's issuer name is that default. webpki finds
   the issuer by **name** and only then fails the signature, so a refusal across two CAs reads `BadSignature`, not
   `UnknownIssuer`. That contradicts `generate_node_cert`'s comment that rustls chains by the SubjectKeyIdentifier. Two
   same-named roots in one store still worked (steps 2 and 3): the path builder tried both. The spike did not test how
   other verifiers handle same-named roots.
4. **The current key, re-issued.** Each node's **current** key was re-issued under the successor, so no new key was
   published. The successor's certificate record went to the same `cert_record_key(node, key)` as the old one and
   replaced it. That the identity history, the revocation standing and `anchors_seen` are unchanged by the overwrite is
   **not measured**. `rotate_identity` still cannot run on the off-node posture (it needs the CA key). A new key under
   the successor was not tried.

## What it could not do, or did not try

- **The succession machinery:** D4's successor-signed record, `tls commit` / `tls succeed`, the window end and act-once.
  The spike calls the reload path by hand.
- **How the successor certificate reaches a node.** The spike wrote it to a file beside the node's own; I2 decides where
  it lives.
- **Persistence and a restart mid-window.** Shown necessary (finding 2) but not built or run.
- **Re-judging the cached verdicts** (`cert_facts`, `anchors_seen`) when the roots change. The spike leaves them as they
  were.
- **The other verifiers and paths:** the gateway on its own `[gateway_tls]` certificate; the bulk fetch (it reads
  `fleet_server_verifier()` per fetch, so it should follow the swap); removal and revocation across the two roots; a
  mixed-version fleet; the secure profile's guarantee report during the window.
- **Certificate records after narrowing**, under either of I2's two rules.
- **A successor issued as an intermediate** under the old root rather than as a second root.
