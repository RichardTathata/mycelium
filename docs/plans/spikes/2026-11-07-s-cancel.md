# Spike S-cancel — 2026-11-07

Wave 1b of [`identity-and-lifecycle.md`](../identity-and-lifecycle.md), settling row I4 (D2). The spike branch is
`spike-s-cancel` at `e8e58b2e`, off `main` at `6a64e8bc`. Its code is throwaway and never merges.

## The question

From the plan, verbatim: *a `call:` mandate minted at admission reaches the provider before its checkpoint gossips.
Carry the first checkpoint **inside the envelope** beside the mandate, through `assess` and `admit_after` to `begin`;
measure the added bytes and the admission latency against today's grant path; show a revoked term read `Refused`; and
two bounds the row must state.* **Done when:** *a call registered with `begin` without a KV round-trip, or the bounded
wait's cost measured; the memory-reclamation hook shown on 10⁵ calls.*

**Answer: carry it.**
- A provider that has never seen the checkpoint establishes the `call:` mandate from the envelope and registers the work
  with `begin`. There is no KV read and no wait.
- The cost is 360 bytes on the presented mandate, and no admission latency beyond today's grant path.
- The alternative, waiting for the checkpoint to gossip, adds the gossip latency to every admission: 27 ms at p50 on
  loopback. Under a partition it has no bound. Without either, the call runs uncancellably, as measured below.

## What was built on the spike branch

- **A `call:` scope** (`CALL_SCOPE_PREFIX`, `Mandate::is_call`) in `src/mandate/grant.rs`.
  - It is entitled as `grant:` is: by the prefix, or fleet-wide for a `node:` issuer.
  - It is exempt from the verifier's per-scope epoch bookkeeping, as grants are.
- **`PresentedMandate.checkpoint: Option<SignedRevocationCheckpoint>`** (serde default; omitted when `None`).
  - `ExecutionAuthority::assess` offers it before reading the standing.
  - It is offered only when its authority and scope are the mandate's own, so a carried checkpoint speaks for nothing
    else.
  - It is offered only when the view does not already hold that sequence.
- **A `call:` branch in `assess`**, judged as a grant is: its window, and its issuer's checkpoint for its own scope.
  - `NotRevoked` gives `Established`.
  - `Revoked` gives **`Refused(MandateRefusal::Revoked { term })`**, a new variant.
  - `Unknown` gives `Unknown`.
- **The sweep** judges `call:` work as it judges grant work.
- **The start rule** exempts a `call:` checkpoint, as it exempts a grant's.
- **The reclamation hook** `ExecutionAuthority::reclaim_calls(now_ms)`, run by every sweep.
  - It forgets a `call:` scope's checkpoints and revoked set **once its mandate's window has passed**, not when its work
    ends.
  - The windows live in a `call_windows` map inside the authority's existing state (lock-order row 43). No lock is
    added.
  - The view gains `RevocationView::forget`.

## What ran

Everything ran on an Apple M2 Max, macOS, Rust 1.96.0.

- **In-process measurements:** `cargo test --release --lib --features tls,compliance,a2a spike_s_cancel::s -- --nocapture --test-threads=1`
  (`src/agent/gateway_authority.rs`, module `spike_s_cancel`, tests `s1`–`s5`). The same five also passed in a debug
  build.
- **End to end over two TLS nodes:** `cargo test --lib --features tls,compliance,a2a spike_s_cancel -- --nocapture --test-threads=1`
  (`src/agent/http/grant_tests.rs`, `spike_s_cancel_end_to_end_over_two_nodes`). This ran in a debug build, two
  in-process nodes on loopback.
  - Node A stands in for the admitting gateway. It mints the `call:` mandate, holding and issuing it itself, signs the
    possession proof and the first checkpoint, and calls B's slow tool (3 s) directly.
  - B is the provider: provider enforcement on, an execution authority with a 2 s freshness window, so it sweeps every
    100 ms.
  - The first checkpoint is never written to any KV.
  - A revokes by writing the revoking checkpoint where a grant's travels, `grant/{holder}/{term}/checkpoint`. B's
    existing feeder offers it to B's authority.

## The two bounds the row must state

1. **A term revoked between the gateway's framing and the provider's `admit_after`.** The call carries a checkpoint
   that predates the revocation, so the provider admits and registers the work, and stops it only when the revoking
   checkpoint arrives.
   - **The cancel's effect is gossip latency, plus the sweep interval, plus the handler's own time to stop.**
   - Measured: 38.7 ms with a 100 ms sweep on loopback.
   - The sweep interval is the gate's freshness window divided by twenty, clamped to 100 ms–5 s. With the 60 s window
     used in S1–S5 it is 3 s, so a deployment's bound depends on its configured window.
2. **`drain_bound` is `Unbounded` for the unenforced and unconfirmable classes** (`src/mandate/authority.rs`). There a
   cancel writes `Refused` and stops nothing the resource can confirm. The cancel's receipt has to name the drain class
   it hit, or answer `DeliveryUnknown`. **The spike did not build that receipt.**

## What it could not do, or did not do

- **No gateway door mints a `call:` mandate.** A node minted it by hand. Admission-time minting, the second mandate
  slot, `is_entitled`'s `call:` arm for a configured gateway, and the holder being the gateway behind a *client's* call
  are all I4's to build. The spike used a member's direct call, whose caller is the holder.
- **The revoking checkpoint was written with a plain KV `set`** under the grant key family, so B's existing feeder
  found it. I4 needs its own `call:` key family and feeder, written durably (`write_record_durable`, as a grant's
  checkpoint is).
- **Not built:** the cancel receipt naming the drain class or `DeliveryUnknown`; the cancel-forward RPC kind; A2A
  `tasks/cancel`; MCP `notifications/cancelled` and its id → term table; `max_drain_secs`; `grant_retention_secs`; the
  `cancellable` declaration key.
- **`PresentedMandate` is public, so adding the field breaks an exhaustive literal.** Here that is six literals outside
  the library: `tests/gateway_mandate_external.rs`, three examples (`authority_drain`, `confined_fleet_node`,
  `composed_commit`) and two in `mycelium-effects/tests/composed.rs`. I4 either makes the struct `#[non_exhaustive]`
  with a constructor, or carries the checkpoint under its own `_meta` key. In both cases it needs an upgrade note.
- **Memory:** every offered checkpoint opens a revoked-set entry for its scope even when it revokes nothing. Reclaiming
  frees the entries, not the process's pages.
- **What was not measured:**
  - the two-node run was a debug build on loopback, not over a real network or under load;
  - the full envelope's bytes against the 8 KiB cap (only the presented mandate's);
  - a restart in the middle (the `call:` window table is in memory only).

## For row I4

**The establishment question is settled: the first checkpoint travels in the envelope, beside the mandate.** Its cost
is measured (+360 B, no latency over the grant path). The two bounds are stated above with a measurement for the first.
The reclamation rule is: keep until the window ends, not until the work ends, so re-presenting a revoked call inside its
window stays refused. The row can now be written from this note.
